## 1. Executive Summary

PlanOne started in a state where it could eventually solve `pylint-dev__astroid-941`, but only after massive token waste and repeated degraded runs. The root problems were not the underlying model’s coding ability. They were mostly orchestration problems:

- silent failures in deterministic localization and reproducer paths
- bad fallback behavior when Gemini failed
- wrong or degraded panel framing
- poor symbol/file disambiguation around the true bug site
- executor hesitation after reading enough context
- dirty-worktree handling issues
- missing env/provider ergonomics

The session progressively fixed these layers.

By the end:

- deterministic localization is far more observable and resilient
- reproducer behavior is trace-visible and much stronger
- OpenRouter fallback diagnostics are in place
- `.env` / `.env.local` loading exists
- Groq provider support exists
- the lightweight “PlanOne Lite” path dramatically reduced token spend
- PlanOne successfully produced the correct astroid fix on a clean run

The correct astroid fix is:

```diff
-        metaclass = self.declared_metaclass(context=context)
+        metaclass = self.metaclass(context=context)
```

The overall conclusion is:

- PlanOne’s original problem was mainly orchestration quality, not model capability
- a direct coding agent could solve the bug much faster
- the work done here moved PlanOne much closer to that behavior by stripping waste and tightening grounding

## 2. The Astroid Task We Used as the Main Debugging Probe

Primary benchmark task:

- SWE-bench instance: `pylint-dev__astroid-941`

Main observed bug in astroid:

- attributes defined as `@property` on a metaclass of a base class were incorrectly inferred when accessed through a derived class
- `Parent.__members__` worked
- `Derived.__members__` failed

Ground-truth fix path:

- actual bug site was in `ClassDef.igetattr()` in `astroid/scoped_nodes.py`
- the key change was:
  - `self.declared_metaclass(context=context)` -> `self.metaclass(context=context)`

Important nuance from SWE-bench:

- PlanOne’s one-line fix handled the metaclass case
- the SWE-bench gold patch also referenced `brain_namedtuple_enum.py`
- the harness showed PlanOne’s initial one-file patch was insufficient under the full official test patch

This astroid task became the main probe we used to uncover PlanOne’s orchestration failures.

## 3. High-Level Timeline of the Session

### Phase 1: Verify PlanOne’s astroid patch against SWE-bench

We verified that PlanOne’s original astroid patch was incomplete under the official SWE-bench harness.

Main findings:

- PlanOne fixed only `astroid/scoped_nodes.py`
- official SWE-bench included broader expectations
- harness showed one fail-to-pass test still failing

This established that “passing some local tests” was not enough. We needed to inspect PlanOne’s upstream framing and trace behavior.

### Phase 2: Inspect the actual run traces and transcripts

We answered several trace questions:

- what approach text the executor received
- what implementation-step prompt it saw
- what deterministic localizer returned
- what the system prompt said
- what the model said when it completed

Main diagnosis:

- deterministic localization had failed silently
- panel degraded and framed the task as a narrow `_get_attribute_from_metaclass` story
- executor followed that narrow story faithfully
- completion rules encouraged it to stop once local tests passed

### Phase 3: Make silent failures visible

We instrumented two key failure points:

- deterministic localizer wrapper in `src/panel/index.ts`
- reproducer flow in `src/intake/reproducer.ts`

Goal:

- no more invisible fallback to degraded mode
- no more mysterious `attempted: false`

Result:

- trace now reveals entry, early exits, exceptions, and fallback reasons

### Phase 4: Discover the real live failure mode

Once trace visibility improved, the real causes became obvious:

- reproducer often returned `NO_REPRODUCER`
- deterministic localization sometimes failed due to Gemini `503`
- later it failed due to Gemini `429`
- later it reached OpenRouter fallback but got `401 User not found`

This was critical: it shifted blame away from vague “model quality” and toward concrete infrastructure and routing issues.

### Phase 5: Make localization resilient

We added:

- retry with exponential backoff
- fallback model routing
- OpenRouter diagnostics
- key fingerprinting
- preflight probe

This let us prove exactly what key PlanOne was using and whether fallback lanes were alive before the run even started.

### Phase 6: Build “PlanOne Lite” and strip token waste

We introduced a lightweight path with large architectural cuts:

- lower tool-iteration cap
- aggressive fail-fast rules
- earlier compaction
- panel disabled
- monitor disabled
- compression passthrough
- direct deterministic localization usage

Result:

- token usage dropped dramatically
- but new bottlenecks appeared in parser strictness, symbol verification, implementation-surface disambiguation, and executor write behavior

### Phase 7: Fix the full chain from localization to write

We progressively fixed:

- file-localization parsing
- symbol-localization parsing
- skeleton fallback behavior
- Python skeleton extraction for class methods
- verified chunk / line disambiguation
- implementation-surface scoring and filtering
- verified-window prompt injection
- write-readiness nudges and executor behavior

Eventually PlanOne successfully produced the correct astroid patch on a clean run.

### Phase 8: Add Groq provider support and `.env` loading

Later work focused on runtime ergonomics and cost reduction:

- added Groq provider support
- routed executor/intake/panel/verifier-model metadata to Groq when `GROQ_API_KEY` exists
- removed dead verifier-provider routing logic
- added Groq preflight
- added automatic `.env` / `.env.local` loading

The user explicitly requested not to run the Groq smoke test. That instruction was followed.

## 4. Core Diagnoses We Reached

### 4.1 Deterministic localization was originally failing silently

Original problem:

- `safeDeterministicLocalization()` caught exceptions and returned `null`
- the trace did not show why
- panel quietly fell back to degraded synthesis

Impact:

- a lot of runs were never actually benefiting from the new localization work

Fix:

- top-level exception is now written to RTS
- stage-level localizer breadcrumbs were added

### 4.2 Reproducer was originally opaque

Original problem:

- `runReproducer()` could return `attempted: false` with no visible reason

Fix:

- trace entry now fires at function start
- every early exit now has a trace-visible reason

### 4.3 Gemini provider outages/rate limits were collapsing the whole localization path

Observed live failures:

- `503 Service Unavailable`
- `429 Too Many Requests`

Original bug:

- only 5xx-style errors were considered retryable for localization fallback
- `429` was treated as non-retryable

Fix:

- `429`, quota, rate-limit, free-tier, and retryDelay patterns are now retryable/fallback-eligible

### 4.4 OpenRouter fallback auth looked broken, but the real issue was wrong runtime key material

We proved:

- the manual OpenRouter key worked in terminal
- PlanOne had sometimes been using a different key than the user expected

Fixes added:

- key fingerprint logging
- OpenRouter preflight

This turned a vague “401 User not found” into a directly diagnosable configuration problem.

### 4.5 BaseMemory was part of the problem, but not the whole problem

Important conclusion reached:

- BaseMemory often returned semantically nearby but wrong neighborhoods
- e.g. `_get_attribute_from_metaclass` looked plausible
- but BaseMemory was not the only cause

Key framing:

- BaseMemory’s contribution was structural semantic-neighborhood bias
- execution evidence was needed to beat semantic lookalikes
- reproducer / traceback signal was the most powerful corrective

### 4.6 Executor hesitation became the final bottleneck

Once localization and symbol handoff were mostly correct:

- the executor could read `igetattr`
- then read `declared_metaclass`
- then read `metaclass`
- and still not write fast enough

This was the final transition bug:

- “understand -> write” was too hesitant

### 4.7 Dirty-worktree handling mattered

One astroid run was falsely treated as failed because:

- the correct patch was already present in the target repo before the run
- PlanOne’s no-write fail-fast gate fired anyway

This exposed a separate “already-fixed repo” behavior gap.

## 8. Remaining Blind Spots / Risks

These are the currently known blind spots that still matter.

### 8.1 Groq `generateJson()` still lacks fallback

File:

- `/Users/aditya3/Desktop/OpenSourceContributions/PlanOne/src/llm/groq.ts`

Problem:

- `generateJson()` currently tries Groq models and then throws
- unlike `generateText()` and `analyze()`, it does not use retryable fallback behavior

Impact:

- prompt enhancement and complexity classification can still hard-fail on Groq 429/503 conditions

Priority:

- high

### 8.2 `.env` loading is cwd-based, not repo-target-based

Files:

- `/Users/aditya3/Desktop/OpenSourceContributions/PlanOne/src/utils/env.ts`
- `/Users/aditya3/Desktop/OpenSourceContributions/PlanOne/src/cli.ts`

Problem:

- `.env` files are loaded from `process.cwd()`
- if the CLI is launched from a different directory than the PlanOne repo, the expected `.env` may not be found

Impact:

- confusing runtime behavior when users invoke the CLI from another shell location

Priority:

- medium

### 8.3 No `--groq-key` CLI override

File:

- `/Users/aditya3/Desktop/OpenSourceContributions/PlanOne/src/cli.ts`

Problem:

- Groq only reads from `process.env.GROQ_API_KEY`
- other providers have CLI key overrides

Impact:

- one-off testing is slightly more awkward and inconsistent

Priority:

- low to medium

### 8.4 Already-fixed target repos still need better handling

Context:

- one earlier run failed because the astroid target repo was already patched
- PlanOne escalated due to “no writes” even though the code was effectively already fixed

Impact:

- awkward behavior on dirty worktrees or resumed benchmark repos

Priority:

- medium

### 8.5 Efficiency is still worse than a direct coding agent on easy bugs

This is not a bug in the narrow sense, but it is strategically important.

Observed comparison:

- a direct coding session could solve the same astroid fix in under a minute with far fewer tokens

Implication:

- PlanOne still has orchestration overhead that may not be justified for simple SWE-bench bugs

Priority:

- strategic / long-term

## 9. Recommended Next Steps

These are the next steps I would take in order.

### 9.1 Fix Groq `generateJson()` fallback

Why first:

- it is a real remaining blind spot
- it affects the Groq branch directly
- it is small and contained

Suggested behavior:

- on retryable Groq error in `generateJson()`, fall back to the configured Gemini intake provider, mirroring the `generateText()` / `analyze()` style

### 9.2 Improve `.env` discovery behavior

Two good options:

- load `.env` from both:
  - current working directory
  - PlanOne repo root
- or load `.env` after CLI arg parsing using the actual execution root / explicit config path

Best practical improvement:

- support a deterministic precedence chain such as:
  - shell env
  - cwd `.env.local`
  - cwd `.env`
  - repo-root `.env.local`
  - repo-root `.env`

### 9.3 Add `--groq-key`

Why:

- consistency with other providers
- easier testing and debugging

### 9.4 Improve already-fixed worktree behavior

Possible policy:

- if target tests pass and a verified target file already contains the intended fix, do not treat lack of new writes as failure

### 9.5 Re-evaluate where orchestration is actually worth it

Strategic question:

- for simple bug-fix tasks, should PlanOne use a much shorter path by default?

Possible answer:

- use a fast lane for simple or strongly localized tasks
- reserve the full multi-stage orchestration for ambiguous or high-risk tasks
